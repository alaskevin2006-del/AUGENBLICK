## 零、职责边界（先定基调）

**定位**：Ekspert = **多轴分类学习引擎**。用户观察一个物体（SVG / 图表 / 照片），同时沿多个**相互独立的轴**判定其特征（如"物种 + 痕迹类型 + 基质"）。核心是"通用引擎 + 数据驱动"——引擎只认识抽象的「轴与值」，不认识具体的足迹/牙齿/陶瓷/化石；新增模块 = 新增一个 `JSON + SVG` 目录，核心代码零改动。

**做什么**（引擎侧）：
- 呈现多轴分类活动（Atlas 图谱 / 单轴测验 / 多轴测验 / 比较 / 决策树消除）。
- 理解专业数据（轴、值、决策树 trees.json、SVG 图形）。
- **给出领域评分证据**：每个轴的判定结果 → `dimensions[]`（这是 Ekspert 最核心的输出）。

**不做什么**（交给平台，引擎不碰）：
- 不裁决对错 → 统一答案求值管线（ADR-0005）。
- 不调度顺序/题集/随机种子/中断恢复 → 编排器（ARCHITECTURE「五方状态归属」）。
- 不管掌握度 / 间隔复习 / 混淆关系 / 跨会话历史 → Learning State。
- 不管导航 / 进度条 / 语言 / 无障碍偏好 → Shell。

**与兄弟引擎的区分**（防止职责重叠）：

| 引擎 | 定位 | dimensions 语义 |
|---|---|---|
| Znawca | 抽认卡（图片↔文字问答） | 0/1 |
| Anvil | 通用题型（Excel 驱动 9 题型） | 0/1 |
| **Ekspert** | **多轴分类（每轴独立评分）** | **各分类轴** |
| Sokole Oko | 视觉区域识别（点中 mask 找区域） | 各区域命中数 |
| Companion | 语音评估（音素·节奏·语调） | 音素·节奏·语调 |

## 一、职责范围（做什么 / 不做什么）

### Q1. 评分系统归属：Ekspert 的「按轴掌握度 / 混淆矩阵 / 间隔重复 / 难度自适应」由谁实现？
- **问题**：EKSPERT.md §5 详细描述了 per-axis mastery coefficient、confusion matrix、SM-2 间隔重复、自动难度调整，看似是引擎自建能力。
- **参考方案**：ARCHITECTURE「五方状态归属」已明确——掌握度、间隔复习、混淆关系、跨会话历史归 **Learning State**；活动顺序、题集固定、随机种子归 **编排器**；引擎只"呈现活动、理解数据、给出领域评分证据"。合约红线「评分/进度/错题/调度规则全放后端」。因此 Ekspert **不实现**这些算法，只输出每轴判定结果（`dimensions[]`），由平台统一裁决与调度。
- **待钉死**：Ekspert 特有的「狐狸↔貉」这类**领域化混淆对**（confuse_with 字段），是引擎在数据里声明、由平台 Learning State 消费？还是引擎输出混淆建议？需确认归属边界（引擎提供"confuse_with 候选对"作为数据，平台做通用混淆跟踪是更干净的分法）。

### Q2. 决策树「独立式」模式的路径正确性判定归谁？
- **问题**：EKSPERT §4.5B「Independent」要求检查用户是否按正确顺序重建决策路径（步骤+顺序都对才得分），这是 Ekspert 特有题型。
- **参考方案**：ADR-0005 统一判分管线目前列举覆盖题型为"填空/匹配/多轴/掩膜"，**未明确覆盖"决策路径顺序正确性"**。需确认是否纳入统一判分管线的扩展规则，还是 Ekspert 以 `dimensions[]` + 自描述证据提交、平台按通用规则裁决。
- **待钉死**：决策树独立式的判分粒度（整路径对错 vs 逐步给分）与证据格式。

### Q3. V1 是否包含「自定义模块编辑器 / 照片导入 / 数据库共享」？
- **问题**：EKSPERT §10.1–10.3 描述了用户自建模块、照片导入、JSON 共享等扩展能力。
- **参考方案**：EKSPERT §11 把「Custom module editor」「Photo import」列在 **Phase 3**，MVP（Phase 1）不含。建议 V1 明确砍掉这四项（自定义模块编辑器 / 照片导入 / 数据库共享 / 田野模式），只做 Phase 1 + Phase 2 核心。
- **待钉死**：V1 范围以 EKSPERT §11 的 Phase 1（单轴+多轴测验、Atlas、tracking 50 条 + teeth 5 物种、基础统计、SVG）为准，是否含 Phase 2（比较模式、决策树、间隔重复、混淆矩阵）需定。

### Q4. 「田野模式」（离线现场鉴定）在 V1 是否砍掉？
- **问题**：EKSPERT §4.6 定义 Field Mode，依赖离线（PWA + 数据缓存）。
- **参考方案**：`docs/边界与验收.md` 明确"V1 = 纯在线 Web，无离线能力；离线后置，将来走原生 App，不是 PWA"；ARCHITECTURE 红线 #3 同。**V1 砍掉 Field Mode**，仅保留决策树作为纯在线学习模式。
- **待钉死**：确认 Field Mode 后置，不进 V1 验收。

## 二、输入输出约定（三份引擎合约）

### Q5. 数据模型：JSON 私有数据如何接入 Excel 交换格式？
- **问题**：EKSPERT §2.2/§3 的数据是 JSON（`data.json` / `trees.json` / `modules.json` + `svg/`），而平台内容交换格式是 Excel（ADR-0004）。
- **参考方案**：ARCHITECTURE「三层内容模型」——第三层是"各引擎私有，对编排器不透明"。AUGENBLICK §3.3 明示"Ekspert 的数据是 JSON 而非表格，Scope 记法映射到命名属性而非列字母，**映射是 Ekspert 内部事，超出平台范围**"。即：Excel 课程脚本（第二层）仍用 B 列指定引擎 + C 列指定数据文件名，E 列 Scope 由 Ekspert 内部翻译成轴名。
- **待钉死**：Ekspert 需自定一套「Scope 表达式 → 轴名」的映射规则并写进 `src/ekspert/docs/边界.md`，供编排器/校验器理解（校验器至少要知道"未知轴名"是错误）。

### Q6. 输入「调用包 JSON」需要 Ekspert 理解哪些字段？
- **问题**：运行时输入的统一格式。
- **参考方案**：合约.md 运行时合约——输入「调用包 JSON」含：稳定课程版本、活动、题目、attempt、随机种子、策略 ID。AUGENBLICK §4.2 补充字段：engine name、resolved data file path、package/checkpoint、scope expression、question types、item count、mode(L/T)、learner sex、interface language、resume token。Ekspert 作为随机引擎需重点处理：`scope`（轴名映射）、`question types`（单轴/多轴/比较/决策树）、`item count`、`mode L/T`。
- **待钉死**：以合约.md（治理定稿）为准对齐字段清单，确认 Ekspert 适配器消费的最终 schema（AUGENBLICK.md 的字段与合约.md 的字段表述略有差异，需统一）。

### Q7. 输出「四事件」与多轴评分如何表达？
- **问题**：Ekspert 是部分分（多轴），需输出每轴结果。
- **参考方案**：合约.md 四事件 `activityReady / itemStarted / itemResolved / activityFinished`，每事件带 `eventId + 顺序号 + 时间戳`（幂等重放）。评分约定：`score 0–1` 归一化 + `dimensions[]`（Ekspert 各轴）+ `attemptNumber/encounterNumber/masteryEvidence/feedbackRef/耗时/错误类型`。AUGENBLICK §4.2 明确"Ekspert returns its partial fraction"（如 4 轴对 3 轴 = 0.75）。
- **待钉死**：`itemResolved` 里 dimensions[] 的精确结构（每轴 id + 用户答案 + 是否正确 + 可选权重），及 `activityFinished` 的 totalScore 汇总口径。

### Q8. `activityReady { itemCount }` 与 `estimateItemCount`？
- **问题**：Ekspert 的题数如何让 Shell 提前画出 Questions 进度条。
- **参考方案**：AUGENBLICK §4.2 说明 `activityReady { itemCount }` 让 Shell 在首题前画出进度条；合约.md 内容编译合约要求引擎声明 `estimateItemCount`。Ekspert 的题数来自 G 列（item count）或 pool 大小。
- **待钉死**：Ekspert 实现 `estimateItemCount`，并确认空白 G 列时按整个 pool 计。

### Q9. SVG 素材如何存放与交付？
- **问题**：Ekspert 每条记录引用 SVG（`media.svg`、`comparative_diagram`），素材放哪、运行时怎么取。
- **参考方案**：ADR-0008 内容存放混合模式——原始 ZIP/XLSX、SVG、图片进**对象存储（S3 兼容）**，编译后的活动载荷与稳定 ID 进 PostgreSQL（JSONB），媒体走短期签名 URL/CDN。SVG 属素材，走对象存储 + 资产清单。
- **待钉死**：Ekspert 的 `modules/*/svg/` 目录在编译时如何进入资产清单、运行时如何解析为签名 URL（适配器 datasource 职责）。

## 三、与其他引擎及平台的接口依赖

### Q10. 与 Anvil 的题型边界（复用度 ~20% 具体指什么）？
- **问题**：进度.md 标 Ekspert 复用度 ~20%（Anvil ~50%）。Anvil 是通用题型引擎（9 题型，Excel 自动检测），Ekspert 的"单轴测验"本质是选择题（4–6 选项，含 confuse_with 干扰项），"多轴测验"是下拉/按钮。两者题型有重叠。
- **参考方案**：需确认这 20% 复用什么。合理分法：**复用的应是平台侧通用件**（Activity Host、统一判分管线、SVG 渲染基础、主题），而非 Anvil 的题型实现——因为 Anvil 面向表格驱动，Ekspert 面向 JSON+轴驱动，题型语义不同。
- **待钉死**：列出 Ekspert 与 Anvil 可共享 / 不可共享的具体清单，明确"复用 20%"的构成（避免误读为"复用 Anvil 引擎"）。

### Q11. 依赖统一 Activity Host（非 iframe）？
- **问题**：Ekspert 的 UI 模块（atlas/quiz-single/quiz-multi/comparison/elimination/statistics）如何嵌入。
- **参考方案**：ADR-0003 统一 Activity Host（主题/尺寸/焦点/键盘/RTL/媒体权限/暂停/退出确认/错误界面），新引擎统一接入 Host，iframe 仅作旧 Znawca 过渡。合约.md UI 宿主合约。Ekspert 适配器应面向 Host 挂载接口，而非 iframe 通信。
- **待钉死**：Ekspert 的 6 个 UI 模块按 Host 合约改造的挂载方式，及键盘全操作（多轴下拉、SVG 交互需满足验收"可完全键盘完成"）。

### Q12. 依赖统一答案求值管线（不自建判题）？
- **问题**：Ekspert 多轴判定、typed input（打字输入更难档）如何判对错。
- **参考方案**：ADR-0005 统一判分（Unicode/大小写/空白/全半角规范化、`H₂O/H2O` 类兼容、同义词由作者确认）——各引擎不自建判题，只提交领域评分证据。Ekspert 的 enum 轴选择天然无格式歧义，但 typed input 需走统一规范化。
- **待钉死**：Ekspert 各轴的题型映射到统一判分管线覆盖的哪一类（enum 选择 = 精确匹配；typed input = 规范化匹配）。

### Q13. 依赖编排器调度（顺序/随机种子/中断恢复）？
- **问题**：Ekspert 的随机化、题集固定、中断恢复由谁负责。
- **参考方案**：ARCHITECTURE「五方状态归属」+ ADR-0009——编排器管活动顺序、题集固定、随机种子、中断恢复；ADR-0009 明确"测试提交才算一次尝试、中断整份重发、学习模式三轮逃逸"。Ekspert 引擎内的随机化（如选项乱序）需遵循编排器下发的随机种子以保可追溯。
- **待钉死**：Ekspert 内部随机化（选项顺序、混淆对选取）必须用编排器的随机种子，保证"题集/随机种子可追溯"验收项。

## 四、部署与运行环境

### Q14. 技术栈冲突：EKSPERT.md 的「后端可选 / localStorage / SQLite / PWA」已被推翻？
- **问题**：EKSPERT.md §2.1 写"Backend optional、fully offline、localStorage/SQLite、Target PWA"，与治理定稿冲突。
- **参考方案**：ADR-0007 技术栈定稿 = **React + TypeScript + Vite 前端 / Django 5.2 + DRF 后端 / PostgreSQL 17（JSONB 存引擎载荷）/ S3 兼容对象存储 / Docker Compose 部署**。合约红线「逻辑全走 API，不进浏览器」。`docs/边界与验收.md`「V1 纯在线 Web，无离线，不做 PWA」。
- **待钉死**：**以治理文档为准，EKSPERT.md §2.1 的技术栈建议作废**。Ekspert 的持久化（用户统计、掌握度）全走后端 API + PostgreSQL，不在浏览器用 localStorage/SQLite。

### Q15. 内容生产规模与 Phase 划分？
- **问题**：Ekspert 四模块内容量巨大（tracking ~177 条、teeth ~240 条、ceramics ~120 条、fossils ~140 条），MVP 到底做多少。
- **参考方案**：EKSPERT §11——Phase 1 仅 tracking（50 物种×足迹=50 条）+ teeth（5 物种，~80 条）；Phase 2 扩 tracking 至 scat/pellet（~100 条）+ teeth 剩余 10 物种；Phase 3 才上 ceramics + fossils 全量。
- **待钉死**：V1 验收以 Phase 1 数据量为准；内容由谁生产、何时交付（进度.md 标 Ekspert"并行准备教学内容"）。

### Q16. 数据驻留与跨境合规是否波及 Ekspert 内容？
- **问题**：Ekspert 教学内容（波兰/中欧物种、波兰化石产地等）与学员数据是否涉 EU 驻留。
- **参考方案**：OPEN-QUESTIONS #10（EU/波兰数据驻留与跨境合规，待评估）+ ADR-0007 回看点（若主要服务波兰/EU 学员，生产前需做合规评估）。此为平台级支线，非 Ekspert 引擎独有，但 Ekspert 内容属地性（波兰）需在内容生产时留意。
- **待钉死**：内容本身无个人数据，预计不阻塞；仅登记为平台支线关注项。
